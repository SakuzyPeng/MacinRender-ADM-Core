# 房间 v1 验证记录

`room-binaural` 已接入离线渲染、文件流式渲染和 Scene 流式渲染，包含 CLI、C ABI v1.47、
房间资源、3DoF、异步切换、seek / epoch reset 和确定长度的排尾。
详细数据和已测核心源码哈希见 [机器可读报告](ROOM_V1_VALIDATION.json)，接口和限制见
[设计文档](REALTIME_ROOM_RENDERING.md)。

下列首次验收及中间优化数据保留为历史基线。当前非 GUI 收尾结论见文末；不能用历史通过
结果覆盖后续复测失败。Linux 32 源零期限超时和 macOS 实机长稳的稳定复现仍未通过。
[`d2db971` 收尾状态与源码清单](ROOM_NON_GUI_CLOSEOUT.json)明确记录当时的通过范围和未通过项；
后续输入控制优化及复测见文末与[优化报告](ROOM_INPUT_SPAN_OPTIMIZATION.json)。

## 数值与声学回归

Rust 1.98.0 Release，在 macOS arm64、Windows x64、Linux x64 上使用同一资源和样本事件，
准备系数、HRIR 查询、直达 / 早反射分支、最终 PCM 和有效帧数逐位相同。
回放包含距离 / 头姿 / 源控制、不同几何房间切换及固定 / 碎片输入块。

- 输出：163,398 帧双耳 f32。
- PCM SHA-256：`b3a3ec3747db934c995289036c7d65eb0224b0726ffc7b8f74aad62a1ffe453d`。
- 22 个标准全频参考位及 6 个补点：28/28 波形重建通过。
- 最大相对 L2：`3.4903576e-5`，门槛 `2e-4`。
- 资源完整性与声学标准判断分开：原 22.2 的固定条件结论保持；正下方补点原有 RT 诊断没有改为通过。

正确性检查包含 13 项 Rust 房间集成测试、7 项内核单元测试、全工作线程零分配检查和
浮点环境恢复检查。macOS Debug 与 Windows 原生检查覆盖 C API、离线 / 文件流式逐位对照、
seek、窗口裁剪、Scene EOS、资源持有、后台切换失败及旧尾声。
C ABI 导出为 152 个 `adm_*` 函数；私有 FFI 247 个函数、79 个结构体与 Rust 一致。

## 桌面实时容量

全部为 Release。内核测试调用 512 帧（预算 10.667 ms），每次调用更新头姿；Scene 流式测试
按 100 Hz 提交头姿，每 5 秒请求一次房间切换，使用默认缓冲策略及 null-device。
未扩大 2048 帧追踪预渲染上限，没有按负载删反射或更改音质。

| 机器 | 32 源静态 P99 | 32 源连续头姿 P99 | 32 源双房间 P99 |
| --- | ---: | ---: | ---: |
| Apple M4 Pro | 1.306 ms | 2.668 ms | 3.606 ms |
| Intel Core i7-11800H / Windows | 2.600 ms | 5.648 ms | 8.432 ms |

上述内核场景均无单次预算超时；1 / 16 源结果也保存在 JSON 报告。

| Scene 场景 | 时长 / 切换数 | 欠载 | 进程 CPU¹ | 峰值 RSS |
| --- | --- | ---: | ---: | ---: |
| macOS，几何变化 | 60 s / 12 | 0 | 164% | 672 MB |
| Windows，几何变化 | 120 s / 24 | 0 | 237% | 511 MB |
| Windows，材料 / 晚场发送变化 | 120 s / 24 | 0 | 248% | 511 MB |

¹ 100% 表示占用一个逻辑 CPU 的处理时间。输出有效帧数均等于素材帧数加声明尾声，EOS 正确。
Windows 房间 DSP 池成功注册 8 个 Audio MMCSS 线程；流式协调线程也采用对应调度。

## Linux 云主机与延迟边界

Linux 云主机完成了房间数值与正确性验证，但没有通过 32 源实时计算预算。
默认 8 个工作线程、512 帧调用时，连续头姿 P99 约 17.389 ms，双房间约 24.273 ms；
16 / 32 线程对照也未满足单块预算。256 帧、187.5 Hz 头姿压力测试同样存在超时，完整结果保留。
这里的 `deadline_misses` 是内核计时，不能改称实际设备欠载，也不能以此推断所有 Linux 机器的能力。
该云主机不在已通过的 32 源实时容量范围内。

macOS / Windows 的控制到 PCM 首次变化均为 257 帧，即 5.354 ms。
这项测量不含传感器、现有预渲染队列、系统或设备缓冲；尚未测量传感器到耳机的实际延迟。
当前交付仍为 48 kHz、worker 头追、单半径 HRIR 距离近似；HOA、GUI、输出阶段头追和多普勒不在 v1 范围内。

## Linux 性能收尾

基于 `606cc40` 保留排尾与切换修复，本轮只优化房间控制状态查询：所有元数据渐变结束后，
`Control::at` 直接返回同一个目标状态，省去每个 PCM 样本重复检查 11 个字段；活动渐变仍按
原有逐字段算法求值。新增截止时间/重新定向/历史查询/重置回归。逐声源输入批处理候选没有
足够明确的额外收益，未保留。默认 8 个工作线程、FFT、音质、缓冲、资源和公开 C API 均未改变。

[本轮完整数据与源码哈希](ROOM_LINUX_PERFORMANCE.json) 分开记录诊断与正式容量结果。
`room-profile` 是默认关闭的 Cargo feature；启用时统计固定大小的跨线程阶段计时，正式容量
测量均关闭它。阶段存在嵌套与并行重叠，不可相加当作 CPU 时间。复现工具及参数见
[性能复测说明](../../scripts/room/README.md#linux-性能复测)。

### 同配置短测

Linux Release、默认 8 线程、32 源、512 帧调用，每个场景 384 次调用，重复三轮。
对照二进制与候选二进制使用相同房间、事件及构建配置，仅控制查询优化不同。

| 场景 | 总 DSP 耗时中位数降幅 | 原 P99 中位数 | 优化后 P99 中位数 |
| --- | ---: | ---: | ---: |
| 静态 | 18.6% | 11.464 ms | 9.548 ms |
| 连续头姿 | 11.6% | 17.780 ms | 16.611 ms |
| 连续头姿＋切房间 | 11.9% | 26.133 ms | 23.619 ms |

1 / 4 / 8 / 16 / 32 线程各重复三轮。32 线程能降低平均处理时间，但连续头姿 P99 中位数仍为
11.225 ms，切房间为 15.062 ms，仍有单次超时；没有据此更改默认线程策略。
分阶段诊断中，4.096 秒音频的连续头姿处理约耗时 4.974 秒，其中工作池往返与执行计时差
约 0.482 秒；响应合成累计约 9.052 秒（含跨线程重叠，其中 HRIR 查询累计约 5.390 秒）。
这些结果显示仍有显著计算成本，不能仅把超时归因于唤醒延迟。

### 长测与容量结论

默认 8 线程、32 源、512 帧调用，每轮的三个场景分别处理 120 秒音频，各 11,250 次调用，
共三轮。切换场景每轮完成 24 次交替切换并回到稳定状态。实例准备/排队耗时单列于计时
窗口之外，进程 CPU 数据仍包含它；这不是异步设备播放测试。

| 场景 | 三轮 P99 范围 | 各轮单次超时数 |
| --- | ---: | --- |
| 静态 | 9.321–9.348 ms | 14 / 14 / 14 |
| 连续头姿 | 15.216–15.361 ms | 11,217 / 11,244 / 11,243 |
| 连续头姿＋反复切房间 | 21.514–21.643 ms | 11,242 / 11,250 / 11,250 |

**这台 Linux 云主机仍未通过 32 源、10.667 ms 单块预算和零超时验收。**
1 / 16 源各三轮短测也有少量或持续超时；256 帧压力测试同样未通过。上述运行均未记录
cgroup CPU 限流或 major page fault，但这不排除缓存/内存带宽或其他调度影响，不等同于
所有 Linux 机器的能力判断。没有使用扩大缓冲、减少反射或降低头姿更新频率来换取通过。

### 一致性与桌面回归

三平台的准备数据、HRIR / 分支、最终 PCM 和有效帧数仍逐位一致，并与原验收回放一致：
163,398 帧，PCM SHA-256 仍为 `b3a3ec3747db934c995289036c7d65eb0224b0726ffc7b8f74aad62a1ffe453d`。
28 个参考点全部通过，最大相对 L2 仍为 `3.4903576e-5`，原补点诊断和声学结论保持。

三平台通过 15 项房间集成测试、8 项房间单元测试、全工作线程零分配和浮点环境恢复检查。
macOS 额外通过启用阶段计时的零分配检查。macOS Debug / Windows 标准 MSVC/Ninja
房间 API 回归通过；当前私有 FFI 为 249 个函数、79 个结构体，与 Rust 一致。

| 当前桌面复测 | 32 源静态 P99 | 连续头姿 P99 | 双房间 P99 | 120 秒 / 24 次切换欠载 |
| --- | ---: | ---: | ---: | ---: |
| macOS arm64 | 1.021 ms | 2.124 ms | 3.192 ms | 0 |
| Windows x64 | 2.179 ms | 5.393 ms | 8.065 ms | 0 |

桌面内核各场景均无单次超时，Scene 流式渲染输出均为预期的 5,827,352 帧。
Scene 进程 CPU / 峰值 RSS 分别约为 macOS 174% / 727 MB、Windows 251% / 511 MB。
桌面历史对照还包含独立的 `606cc40` 修复，不能把跨版本差值全部归因于本轮控制优化。
控制到 PCM 首次变化仍为 257 帧；传感器、主机队列及设备的端到端延迟仍未实测。


## 本轮 Linux 优化复测

在屏幕映射与通用 HRIR 工具之后，复用既有缓存完成共享输入历史、单次工作池交接和 HRIR
重复存储移除。湿声分流先复制历史，再独立推进；归约顺序、标量 FFT、逐频点运算顺序及分别
舍入保持不变。Linux 默认使用有效 CPU 配额/亲和性并行度，最多 32 线程；macOS/Windows
仍最多 8 线程，`MR_ADM_ROOM_WORKERS` 覆盖继续有效。8 列 FFT 候选没有稳定收益，未保留。

[本轮机器可读证据](ROOM_LINUX_CLOSEOUT.json)记录了逐项三轮交替对照及源码哈希。
合并工作池交接把 10 秒对照中的双房间 P99 中位数从 13.851 ms 降到 11.671 ms；去除重复
HRIR 表节省约 12.6 MB 驻留空间。冻结资源的 163,398 帧回放仍保持原 PCM 哈希。

最终容量复测为每个场景三轮 120 秒、32 源、512 帧、32 工作线程、阶段计时关闭。

| 场景 | 三轮 P99 (ms) | 三轮期限超时次数 |
| --- | --- | --- |
| 静态 | 6.998 / 6.692 / 6.725 | 3 / 3 / 3 |
| 连续头姿 | 9.035 / 8.979 / 9.122 | 7 / 12 / 8 |
| 连续头姿、约每 5 秒切房间 | 11.173 / 10.915 / 10.942 | 270 / 180 / 177 |

**Linux 32 源验收仍未通过。** 每轮 24 次房间切换；所有场景均存在超过 10.667 ms 的调用。
这些是 DSP 期限超时，不能记作设备欠载，也不能由 P99 改善推断已满足零超时要求。

## 非 GUI 资源、屏幕与设备收尾

通用 SOFA 工具已覆盖双耳顺序、坐标、非零/分数/负 `Data.Delay`、44.1/48/96 kHz 和完整网格
校验。三种真实输入各有 8,802 个节点；48 kHz 生成包在三平台加载、重建的最大相对 L2 同为
`2.230680889471022e-7`，门槛 `2e-5`。完整数据见 [HRIR 工具验证](ROOM_HRIR_TOOL_VALIDATION.json)。
制作屏幕元数据、CLI `--screen-config`、C ABI v1.47 的新增入口已覆盖三种渲染流程；
[带屏幕事件的三平台回放](ROOM_SCREEN_REPLAY_VALIDATION.json)逐位一致，仍输出 163,398 帧。
未启用重放屏幕的冻结回放保持原哈希。现有公开 C POD 布局和函数签名不变。

冻结的 28 点原始 BRIR 重新直接比对通过，最大相对 L2 `3.4903576e-5`，门槛保持 `2e-4`。
[冻结回归](ROOM_FROZEN_REFERENCE_REGRESSION.json)与[校正包声学报告](ROOM_CORRECTED_ACOUSTIC_VALIDATION.json)
分开保存。校正包 ID 为 `reference-7x6x3.2-corrected-v1`，清单 SHA-256 为
`40495a7c441c77d4b430e7b97278a42ee53786707ecb585a91fafe6ce596bdec`；原冻结包未改。
完整 28 点全向响应在 macOS、Windows、Linux 上逐位相同，也通过了原始验收脚本方法的
[独立交叉核对](ROOM_ACOUSTIC_REFERENCE_METHOD.json)。

正下方 1.05 m 补点的直达能量约为正前方 2.1 m 测点的四倍，晚场能量接近；完整响应的
−5 至 −25 dB 拟合因而更受快速直达/早反射衰减影响。校正保留直达与早反射字节，修改共同
晚场方向变换、公共指数包络及全局发送量。未做逐方向增益归一化、尾部裁短或门槛放宽。
28 点最大通道频响差由 2.684 dB 降至 1.986 dB，门槛仍为 2 dB。适用位置、分支诊断、
原始/校正包身份及制作定义见[声学收尾证据](ROOM_ACOUSTIC_CLOSEOUT.json)；这些是指定几何、
监听位置与固定距离校准下的模型测量，不是任意位置或物理房间的完整标准认证。

无 GUI 设备工具现可指定真实输出、虚拟输入或 WASAPI 回环，并通过真实 OSC 接收器应用
100 Hz 模拟头姿。Windows 旧低频率发送及 EOS 后误请求切房间的探针问题已修正；这些旧跑次
不计为设备通过证据。最终 Realtek 30 分钟运行完成 360 次切换、180,152 次头姿应用，
零欠载、无异常 EOS/处理失败，有效输出 86,467,352 帧。后 15 分钟 RSS 基线约 487 MB，
随切换在约 383–532 MB 间变化，最后 10 分钟趋势约 −0.20 MB/min，没有持续上升趋势。

macOS 扬声器首轮 30 分钟为零欠载；相同房间、DSP 源码和标称负载的后续 30 分钟复测出现
116 次回调供数不足。两次帧数与 EOS 均正确，但不能据首轮通过宣称长稳已经稳定通过。
后续复测使用交流供电，没有系统温度/性能警告，同时存在浏览器和 WindowServer 活动；
这些观察不证明欠载原因。保留通过和失败的完整时序、内存及控制计数。
专用 DSP 线程 QoS 候选的三轮短测为零欠载，但较长试验仍出现欠载，已撤销；
[候选对照和失败证据](ROOM_MACOS_SCHEDULING_CANDIDATE.json)保留，最终 macOS 二进制与上述
116 次欠载的复测二进制完全相同。macOS/Windows 默认线程数和调度策略保持原状。

WASAPI 回环的 30 个有效相关窗测得输出回调至捕获回调延迟 P50 60.828 ms、P99 60.833 ms，
不确定度下限均为 20.021 ms。BlackHole 宽带信号短测为约 29.996 ms，下限同为 20.021 ms。
这些值只覆盖所选软件回环，排除传感器、OSC、渲染和预渲染队列；未校准驱动时间戳、时钟
漂移、重采样及调度误差，不能解释为传感器到耳机的物理延迟。欠载计数也只覆盖应用可观察的
回调供数不足。完整计数与测量范围见[设备证据](ROOM_DEVICE_VALIDATION.json)。

## 输入控制复用优化

以 `d2db971` 的 Rust 实现为基线，在控制事件与 256 帧内部 block 边界之间按声源处理连续
输入。元数据和 live override 的插值均已结束时，只合并一次控制状态与屏幕坐标；仍有斜坡
时逐采样求值。扩散延迟、头锁定过渡和音频历史继续逐采样推进。

Release、32 源、48 kHz、512 帧调用的基线与优化版本交错运行各三轮，每场景每轮 938 次
调用；以下 P99 为三轮 P99 的中位数。macOS 保留 8 个工作线程，Linux 保留 32 个。

| 平台与场景 | 平均调用耗时中位数，优化前 → 后 | P99，优化前 → 后 |
| --- | --- | --- |
| Linux 连续头姿 | 5.515 → 3.158 ms | 7.623 → 4.596 ms |
| Linux 头姿与切换 | 6.588 → 3.765 ms | 10.329 → 6.442 ms |
| macOS 头姿与切换 | 2.267 → 2.155 ms | 3.867 → 3.463 ms |

Linux 随后完成三轮、每场景 120 秒音频的长测，共 101,250 次 DSP 调用。第一、三轮零超时；
第二轮静态 3 次、切换 1 次超时，最大 12.620 ms，故 **零期限超时验收仍未通过**。
本轮没有重新进行实机 30 分钟长稳验收。

三平台的冻结回放和带屏幕回放保持原哈希及 163,398 帧；28 点冻结 BRIR 最大相对 L2 仍为
`3.4903576e-5`，校正包 28 点全向响应字节及声学结论不变。新增回归以逐采样调用对照连续
片段，覆盖同采样点事件、block 边界、斜坡与清除、LFE、缺省 PCM、头姿和完整排尾；三平台
房间集成与全线程零分配测试均通过。源码哈希、各轮数据和验证范围见[优化报告](ROOM_INPUT_SPAN_OPTIMIZATION.json)。

冻结与屏幕回放仍逐位一致。用法及计数解释见[工具说明](../../scripts/room/README.md#linux-性能复测)。

一条 Linux 静态慢调用为 11.484 ms，其中声源任务组 9.354 ms，声源任务累计墙钟与累计
线程 CPU 时间相差约 8.341 ms；另一条头姿慢调用的 21.654 ms 中有 16.231 ms 位于晚场阶段。
两条调用的外部工作交接额外耗时约 0.065 / 0.057 ms。任务组驱动线程的 CPU 时间不包含其它
工作线程，这些数据不能直接证明系统抢占，也不能归因到上一轮未插桩长测的四次超时。

128 / 512 频点 HRIR 分块和每任务至少两项的调度实验均未取得稳定的整体收益，已撤回。
本轮没有新增正式 DSP 优化或设备通过结论；各时段主机负载变化下，仅采用同轮交错对照
判断候选收益。记录见[慢调用与实验报告](ROOM_TAIL_INVESTIGATION.json)。

## 目标滤波器构建

在上述输入控制复用版本上，分区 FIR 现在直接复制到既有 FFT 工作区，只将剩余部分补为
正零，省去中间时间缓冲区的清零及二次复制。动态目标在修改状态前仍校验整条响应，包括
结构支持范围外的非有限值；已校验的数据不再重复扫描。FFT 分解、舍入顺序及滤波器渐变不变。

Release 单声源微基准使用八个头姿的完整响应，按实际结构支持长度构建直达声及早期反射
目标，并在计时外推进卷积历史。预热 32 次后每轮测量 6,000 次，前后版本交错各三轮。
以下为三轮平均耗时的中位数；这不是完整渲染的加速比例。

| 平台 | 直达声目标，前 → 后 | 早期反射目标，前 → 后 |
| --- | --- | --- |
| macOS M4 Pro | 12.13 → 10.05 μs（−17.2%） | 18.22 → 15.80 μs（−13.3%） |
| Linux Xeon 8352V | 25.00 → 20.90 μs（−16.4%） | 37.24 → 32.59 μs（−12.5%） |

完整渲染保持 32 源、512 帧调用、macOS 8 / Linux 32 工作线程，先各做三轮 938 次调用，
再因 Linux 切换场景出现回退而延长到各三轮 2,814 次调用。保留两批结果。延长复测期间，
同一 Linux CPU 集合内观测到六个约占满单核的 NumCalc 进程，且基线耗时也明显上移；
这些数据不能确认 Linux 整体收益。macOS 延长复测三组配对的头动和切换平均耗时均下降，
但候选版本仍有一次期限超时，不能据此宣称期限尾部或实机长稳改善。

三平台冻结与屏幕场景的完整回放清单均与优化前一致；各平台 50 个库单元测试、2 个 FFT
测试、17 个房间集成测试及零分配测试通过。28 点冻结 BRIR 误差和校正包逐点响应报告不变。
普通 Release CLI 已重新构建；未重新进行 30 分钟设备验收。全部数据和构建身份见
[目标滤波器优化报告](ROOM_TARGET_FILTER_OPTIMIZATION.json)。

同日移除 NumCalc 负载后的复测沿用同一组二进制和资源，哈希均核对一致，再交错运行三轮，
每场景每轮 2,814 次调用。运行前容器 CPU 占用约为 0.03 个核；运行中每 10 秒采样，
30 次采样未观测到 NumCalc，也未观测到其它进程平均占用达到 0.15 个核，容器 CPU 配额
限流计数没有增加。这不排除采样间的短暂干扰、宿主调度或频率变化。

| Linux 场景 | 平均调用耗时中位数，前 → 后 | P99 中位数，前 → 后 | 超时次数，前 → 后 |
| --- | --- | --- | --- |
| 静态 | 3.484 → 3.507 ms | 5.607 → 5.503 ms | 3 → 1 |
| 连续头姿 | 5.620 → 5.510 ms | 7.927 → 7.590 ms | 9 → 8 |
| 头姿与切换 | 6.333 → 6.238 ms | 9.847 → 9.816 ms | 31 → 33 |

三组配对的头动和切换平均耗时均下降；三轮中位数分别降低约 2.0% 和 1.5%。每个版本
共测 25,326 次调用，基线 43 次、优化版 42 次超过 10.667 ms 期限，仍未通过零超时门禁。
这次复测支持该负载下的小幅平均耗时收益，但不能证明偶发慢调用已经改善，也不能把此前
超时全部归因于 NumCalc。此次仅补充性能证据，运行时源码未变，未重复正确性及设备验收。

## 晚场单次遍历

每个内部块的晚场改为一次方向遍历：每个世界方向依次渲染当前房间（以及切换中的新房间）的
晚场 FIR、按排尾截止合并，再按头姿分段解码，之后仍按方向编号顺序累加。解码只在头姿变化处
切分，声源几何事件不再触发 32 方向的并行解码。每块只向房间工作池交接一次，少于 4 个声源的
会话也一样（原来每块需要两次以上）。数值和归约顺序不变。

验证以 `45c134d` 为基线，在 Linux x64 云主机（4 vCPU）上使用参考预设
`reference-7x6x3.2-corrected-v1` 和公开的 SADIE II D2 SOFA（8802 个节点）。这不是验收用的私人 HRIR。

- 8 个场景的整段输出与基线逐位相同，1 个和 4 个工作线程都已检查。场景覆盖逐调用头姿、
  切换的预热/淡化/排尾、错开的几何斜坡、块中间的头姿标记、1–3 个声源和 LFE。
- 新增两项房间集成测试：单次遍历与原"晚场 → 合并 → 按每个控制标记解码"路径逐位比较，
  包括排尾截止、新房间进出和部分标记改变头姿；重复声明位置的几何命令不改变会话输出。
  单次遍历分别在测试线程（串行分支）和房间工作线程上（12 个方向，并行分支）运行，参照路径全程串行；
  只在并行分支错配方向的变异会使该测试失败，仅靠会话级测试发现不了。
  房间集成测试共 19 项，零分配测试和 rustfmt / clippy 通过。
- 冻结包的三平台 `room_replay` 需要私人 HRIR，本轮未运行；C++ ctest、桌面平台和设备验收也未重做。

改动前后的二进制交替运行三轮，每次调用 512 帧，没有其他负载。下表为三轮的中位数：

| 场景 | 平均耗时，前 → 后 | P99，前 → 后 |
| --- | --- | --- |
| 8 个声源，全部斜坡，事件分散在 4 个偏移 | 10.78 → 9.23 ms | 18.34 → 16.04 ms |
| 32 个声源，同上 | 29.92 → 27.92 ms | 38.10 → 36.08 ms |
| 1 个声源，逐调用头姿 | 2.45 → 2.13 ms | 4.80 → 4.51 ms |
| 32 个声源，逐调用头姿 | 8.69 → 8.50 ms | 13.47 → 12.11 ms |
| 32 个声源，静态 | 2.63 → 2.53 ms | 5.97 → 5.42 ms |
| 32 个声源，头姿与切房间 | 11.37 → 11.45 ms | 19.51 → 18.72 ms |

收益集中在控制标记多和声源少的会话：8 源错开事件场景超过 10.667 ms 的调用由 374 次降为 143 次。
32 源静态、头动和切换场景的变化在本机噪声范围内。这些结果只适用于该机器，不能代替 32 线程 Linux
或桌面平台的容量复测。数据、哈希和源码身份见[晚场单次遍历报告](ROOM_LATE_PASS_OPTIMIZATION.json)。

斜坡中的声源当时仍在每个全局控制标记处重建；下一节按 ADR 0019 改为各声源自己的更新网格。

## 按声源更新网格

按 [ADR 0019](../adr/0019-room-per-source-update-grid.md)，每个声源只在会话级更新点（块起点、头姿变化、
声源集合变化、输入结束）和自己的几何事件、初始命令、实时覆盖变化处重建几何与目标滤波器。
其他声源的事件不再让它重新取样斜坡。

验证以 `ec02592` 为基线，机器、预设和 HRIR 与上一节相同（Linux x64 云主机 4 vCPU，
`reference-7x6x3.2-corrected-v1`，公开的 SADIE II D2）。

- **逐位对比。** 11 个会话场景中，静态、逐调用头姿、头姿加切换、单声源、含 LFE 的静态场景，
  以及所有声源事件都落在块起点的斜坡场景（共 7 个）逐位相同；4 个声源事件错开在块中间的斜坡场景
  按预期改变。按 `room_replay` 同一调度换用 SADIE 渲染（32 个声源，含 head-locked 声源、增益事件、
  head-locked 切换、移除声源、房间切换和输入结束），有无屏幕两种情况下，固定与碎片分块的 PCM
  SHA-256 都与基线相同。冻结包的哈希仍需维护者在三平台确认。
- **测试。** 新增两项房间集成测试：其他声源在块中间重复声明位置、重复提交相同的实时覆盖时，
  world 与 head-locked 斜坡声源的输出逐位不变；32 个声源各自偏移的斜坡正常渲染，固定与碎片分块
  逐位一致。两项在基线代码上都失败，前者从第 294 帧起不同，后者报 16 个目标的上限错误。
  `room_no_alloc` 加入 8 个声源各自偏移的逐块斜坡后仍为零分配。房间集成测试共 21 项，
  Rust workspace 测试、rustfmt、clippy（含 `room-trace`）通过；C++ debug 构建的
  `mr_adm_room_tests`、`mr_adm_room_trace_tests`、`mr_adm_room_device_probe_tests` 通过。
- **`room_bench` 分段数。** 用 `room-profile` 构建、在合成资源包上运行 128 次 512 帧调用：静态和头姿场景
  每个声源每块 1 段，新增的斜坡场景每块 1.5 段（每次调用 2 个块起点加 1 个自身事件），
  1、16、32 个声源相同。基线代码运行同一场景时，16 和 32 个声源都报 16 个目标的上限错误。

改动前后的二进制交替运行，每次调用 512 帧，没有其他负载，取各轮中位数。头姿两行为 5 轮，
其余为 3 轮。第一次 3 轮测量中 32 源头姿场景新版本略慢，5 轮重测反而略快，二者都在本机噪声范围内。

| 场景 | 平均耗时，前 → 后 | P99，前 → 后 |
| --- | --- | --- |
| 8 个声源，全部斜坡，事件分散在 4 个偏移 | 10.25 → 7.66 ms | 16.33 → 12.21 ms |
| 32 个声源，事件分散在 4 个偏移 | 29.23 → 21.40 ms | 46.51 → 30.55 ms |
| 32 个声源，事件分散在 8 个偏移 | 47.52 → 22.95 ms | 66.03 → 33.32 ms |
| 32 个声源，事件分散在 16 个偏移 | 92.63 → 22.67 ms | 114.24 → 29.42 ms |
| 32 个声源，逐调用头姿 | 8.98 → 8.50 ms | 14.39 → 13.16 ms |
| 1 个声源，逐调用头姿 | 2.10 → 2.06 ms | 4.12 → 4.04 ms |
| 32 个声源，静态 | 2.65 → 2.57 ms | 5.84 → 5.71 ms |

斜坡场景的耗时不再随不同偏移数增长。8 源场景超过 10.667 ms 的调用由每轮 80–168 次降为 7–12 次。
32 源全部斜坡在这台 4 vCPU 主机上前后都超过期限；每块仍要为每个斜坡声源至少重建一次，
这部分成本按 ADR 0019 的"影响"另行处理。这些结果只适用于该机器，不能代替 32 线程 Linux
或桌面平台的容量复测。数据、哈希和源码身份见[按声源更新网格报告](ROOM_PER_SOURCE_GRID.json)。

维护者随后在三个平台用 `room_bench` 的斜坡场景（32 个声源、每次调用 32 个不同事件偏移、
连续头姿，共 2,814 次调用）复测，超过 10.667 ms 预算的调用为 macOS 16 次、Windows 2,804 次、
Linux 2,814 次。按声源更新网格消除了上限报错和随偏移数增长的开销，但 32 个声源同时持续运动
在 Windows 和 Linux 上仍不满足实时预算，macOS 也没有做到零超时。

## 斜坡期间早反射降频评估

[ADR 0020](../adr/0020-room-reflection-grid-during-ramps.md)（提议）在声源几何斜坡期间、头姿不变时，
只在绝对样本位置为网格长度 G 整数倍的块起点更新早反射与晚场发送，其余更新点只更新直达路径。
该行为目前是默认关闭的评估开关 `MR_ADM_ROOM_REFLECTION_GRID`，接受或否决后删除。

验证以 `7d92315` 为基线，机器、预设和 HRIR 与上一节相同。

- **开关关闭。** 11 个会话场景以及 `room_replay` 同一调度（有无屏幕，固定与碎片分块）与 ADR 0019
  构建逐位相同。
- **开关打开（G = 1024）。** 与草拟原型的输出逐位相同。没有几何斜坡的场景不变；32 源全部斜坡场景
  相对开关关闭为 -54.6 至 -61.8 dB，单声源快速运动为 -41.3 dB（最大样本差为峰值的 2.7%），
  `room_replay` 调度为 -47.5 至 -48.2 dB（3.5%），完整表格见 ADR。
- **测试。** 新增一项房间集成测试：静态、head-locked 和 LFE 声源、逐调用头姿、块中间的跳变与增益斜坡、
  房间切换，在 G = 1024 时与关闭时逐位相同，非法网格长度被拒绝。32 个声源各自偏移的斜坡测试分别在
  关闭和 G = 1024 下检查固定与碎片分块逐位一致，并确认两者输出不同。把"几何斜坡"改为"任意斜坡"的变异
  会使第一项从第 334 帧起失败。`room_no_alloc` 打开 G = 1024 后仍为零分配。房间集成测试共 22 项，
  Rust workspace 测试（41 组、275 项）、rustfmt、clippy（含 `room-trace` 与 `room-profile`）通过；
  C++ debug 构建的 `mr_adm_room_tests`、`mr_adm_room_trace_tests`、`mr_adm_room_device_probe_tests` 通过。

同一二进制交替运行，每次调用 512 帧，3 轮取中位数：

| 场景 | 平均耗时，关 → 开 | P99，关 → 开 | 超时，关 → 开 |
| --- | --- | --- | --- |
| 32 个声源全部斜坡，16 个偏移，连续头姿 | 26.98 → 15.82 ms | 38.60 → 21.51 ms | 100/100 → 100/100 |
| 32 个声源全部斜坡，16 个偏移，无头动 | 25.31 → 12.04 ms | 41.08 → 23.63 ms | 100/100 → 55–63/100 |
| 8 个声源斜坡，4 个偏移，连续头姿 | 8.73 → 5.75 ms | 13.46 → 10.75 ms | 21–33/300 → 0–8/300 |
| 单线程，32 个声源全部斜坡，连续头姿 | 87.93 → 44.43 ms | 111.39 → 57.98 ms | 40/40 → 40/40 |

仍每次超时，但这台主机在 32 源只有头动时也超时，不能据此判断维护者机器上的结果。
