## 1. 首轮单组件数量与 Profile 结果

| 对象数 | 默认 `5/0, 31/6` | 诊断上限 `5/1, 31/6` | 诊断上限 `5/2, 31/6` |
| --- | --- | --- | --- |
| 1 | 成功，实际 `5/0` | 成功，实际 `5/0` | 成功，实际 `5/0` |
| 7 | 成功，实际 `5/0` | 成功，实际 `5/0` | 成功，实际 `5/0` |
| 8 | 初始化返回 `!stt` | 成功，实际 `5/1` | 成功，实际 `5/1` |
| 24 | 初始化返回 `!stt` | 成功，实际 `5/1` | 成功，实际 `5/1` |

“默认”仅指能力表未经修改，所有对象用例仍使用私有 `acs ` 属性。
诊断仅替换自建编码进程中一个实例的能力表指针；没有修改系统组件文件，也没有调整解码器的能力表。
`5/2` 是允许上限，不能把该组生成的 8／24 对象样本称为实际 Profile 5 / Level 2。

每个数量样本长 1 秒、48 kHz、每对象一个独立单音，频率为 `440 + 53*i` Hz。
原生解码后有效帧数均为 48,000；音频通道、内部对象／组编号和位置逐一对应。
7、8 对象样本的最低预期频率能量占比为 99.99727%，24 对象为 **99.99111%**；每路最大频谱峰都对应自己的输入频率。
元数据通道单独计数：本轮 N 对象使用 N 路音频加 1 路元数据 PCM 输入，APAC 输出为 N 路对象音频。

## 2. 已打通的输入协议

实现位于 `scripts/research/apac_objects/`，独立编译运行，不进入默认 CMake、CTest 或产品导出流程。

### 编码设置

通过系统 `aenc/apac/appl` 组件创建 AudioCodec。按以下顺序设置：

1. 输入为 48 kHz、交错 Float32 PCM、N+1 通道；输出为 `apac`、48 kHz、N 通道。
2. 用 `acs `（尾部空格）传入 `CFDictionaryRef`，字节数为指针大小。
3. 设置总目标码率 `256000*N` bit/s、`csrc=7`、`cdrc=0`、`aspf=75`，然后初始化并实际送入音频。

最小字典结构如下，`max` 均为包含式索引：

```text
version = 1
sub version = 2
parameters = [
  { key: "Audio Scene Components", ASComponents: [
      { key: "Object", Object: [
          { key: "Object Count", current value: N },
          { key: "Channel Map", current minimum range: 0, current maximum range: N-1 }
      ] }
  ] },
  { key: "Codec Configurations", ASComponents: [ 同样的 Object 配置 ] },
  { key: "APAC Metadata", Metadata: [
      { key: "Channel Map", current minimum range: N, current maximum range: N }
  ] }
]
```

LLDB 实际观察到了类型 1 的 `CreateEncoderElement`、`APACObjEncoder::ReadASCCodecParam`、
`InitializeASCConfig`，以及类型 7 的元数据通道路径。

`achm` 是另一种单项通道映射属性：该版本的 32 位值由音频类型、起始通道和末尾通道组成，
设置时会重建映射向量。本轮采用能一起表达对象与元数据映射的 `acs ` 字典。

**`cumo=1` 不是开启对象编码的必要条件。** 实现检查和实际调用均显示该模式进入
`APACCustomModeEncoder` 的附属帧处理分支。空元数据对照中它初始化成功，但没有产出音频包。
所有成功对象样本均保留普通模式，即不设置 `cumo`。

### PCM 元数据内容

本轮采用 AIA 1.4 的非 live 输入形式。位置字节流使用大端位序，整体通过小端有符号 16 位字承载；
将每个字除以 32768，放入附加 Float32 元数据通道。编码器会恢复这些 16 位字，再解析元数据。
直接把整数幅度放进 Float32 通道会受到音频输入钳位，不能作为等价传输。

每 1024 个采样点输入一份元数据：

- 7 字节头：`0xFFFF`、16 位总字节数、版本 `1.4`、标志 0。
- 静态 chunk 数为 0，动态 chunk 数为 1；动态块为 `apdd`，后跟 16 位 payload 字节数。
- payload 描述组数量、各组更新、顺序组编号、一个时间块及 renderer parameter 0（位置）。
- 本轮使用参考坐标框架 0、球坐标、Float32 角度／距离；关闭旋转，不指定块内起点和时长。

最小编码实现见 `make_inputs.py`。每个对象在每个元数据帧都明确给出位置。
组编号按输入对象通道顺序分配为 `0..N-1`，尚未定义与 ADM 字符串对象 ID 或多轨对象的产品映射。

另检查了 `BinaryMetadataReader`：不提供 PCM 元数据通道时，私有 `mdpf=1` 能使运行过程触达其
`GetMetadata`。本轮只验证了该 reader 的选择与空输入行为，尚未验证独立二进制 payload 的提交接口。
成功位置样本全部使用上述 PCM 通道协议。

## 3. 位置、时间与渲染验收

解码探测程序只读取压缩包、magic cookie、格式及包索引，不读取输入轨迹。
位置通过 LLDB 在原生位置反序列化后的 `ItemPosition::DeriveAbsolutePosition` 入口只读采集，
记录重建球坐标、量化整数、组编号、解码包号和 PCM 样本计数。软件断点不改变解码配置和算法。
解码完成后才按 packet timing 去除前导／尾部填充并导出位置 CSV。

本轮默认位置精度实测为方位 9 bit、仰角 8 bit、归一化距离 7 bit。
方位的普通量化步长为 `360/512 = 0.703125°`，本轮样本均落在半步长误差内。
位置范围和精度选择仍需结合静态配置解释；本轮实测范围是水平角约 ±150° 内、仰角 0°、距离 1。
不把这些实测扩展为所有参考框架、距离范围、笛卡尔坐标或旋转字段均已验证。

| 样本 | 长度 | 读回位置结果 | 离线双耳结果 |
| --- | --- | --- | --- |
| 左 60° | 1 秒 | 59.765625°，误差 0.234375° | 左耳相对右耳约 +4.94 dB |
| 右 60° | 1 秒 | -59.765625°，误差 0.234375° | 左耳相对右耳约 -4.48 dB |
| 左停留 → 移动 → 右停留 | 3 秒 | 最大方位误差 0.3475° | 前段 +4.94 dB，末段 -4.48 dB |

移动轨迹为左侧停留 0.5 秒、2 秒匀速移到右侧、再停留 0.5 秒。
更新间隔为 1024/48000 秒，约 21.333 ms；去除编码前导后，全部更新样本位置与输入时基对应。
ASP 同步包可能引入额外的反序列化调用，采样时使用实际 PCM 计数合并同一音频位置的更新，
不能直接用函数调用次数代替音频时间。

原生编码器前导为 2048 帧；1 秒样本尾部填充 128 帧，3 秒样本尾部填充 384 帧。
直接 AudioCodec 调用必须反复送入零长度输入并排空，直到返回 EOF；第一次返回 needs-more-input 不代表排空完成。
该版本的原生 APAC 解码接口输出请求按 codec packet 检查容量，探测器每次请求一个包，并按返回的 PCM 帧数记账。

离线渲染使用 AUSpatialMixer PointSource / HRTFHQ，仅输入解码得到的音频和位置；
APAC/ADM 的正方位向左，传给 SpatialMixer 时反转方位符号。
这里验证的是 **自建“解码对象音频＋解码位置→系统渲染器”管线**。
本轮没有验证普通播放器直接采用 APAC 对象元数据的空间播放效果，也没有验证其插值策略、头部跟踪或 Vision Pro。
离线探测以元数据帧为粒度更新参数，不宣称已有额外的子帧轨迹精度。

## 4. 容器、反例和证据边界

左右静态、移动，以及 7／8／24 对象样本均封装为 CAF，再用 `afconvert -f mp4f -d 0` 复制到 MP4。
CAF 没有另写任意声道坐标。通过原生 AudioFile 接口重新读取两种容器，压缩包均与编码产物逐字节一致，
有效帧数、前导和尾部填充也一致。

AVAssetReader 完成了上述 12 个文件的 PCM 读取：声道数正确，1 秒为 48,000 帧、3 秒为 144,000 帧，
均非静音。这是容器读取兼容性证据，不等于系统直接对象空间播放已通过。

受控反例：

| 输入 | 系统行为 | 探测器判定 |
| --- | --- | --- |
| 对象存在但未提供元数据通道 | 可产生、解码音频，没有所需对象位置事件 | 位置闭环不通过 |
| 元数据通道全零 | 可产生音频，读回默认 `(-180°, -90°, 0)` | 目标位置校验不通过 |
| Object Count 与通道范围不一致 | `acs ` 设置返回 `!dat` | 配置被拒绝 |
| 8／24 对象、默认能力表 | 初始化返回 `!stt` | 默认数量边界被拒绝 |

验证器检查逐对象频率、帧数、完整位置时间线、组编号、量化误差和渲染方向；
它不会把返回 0、存在输出文件或音频非静音单独当作对象位置成功。
LLDB 退出状态与被调试程序的退出状态分别记录，避免调试器成功退出掩盖探测程序失败。

## 5. 复现与 Core 接续

在本 checkout 使用新目录运行：

```sh
python3 scripts/research/apac_objects/run_experiments.py \
  --output local/apac-object-experiments/new-run
```

依赖系统 Xcode clang／LLDB、AudioToolbox／AVFoundation、Python 3 和 NumPy。
原生工具均为 `-O2 -g`；普通用例 30 秒、调试用例 60 秒超时，超时终止整组自建子进程。
输出目录必须不存在；探测产物也拒绝覆盖已有文件。
完整重跑不需要 IDA。需要重新推导协议时，`ida_extract.py` 可对一份本地数据库按符号筛选；
系统镜像、数据库、反编译原文不进入交付包。

版本绑定的 arm64e 切片 SHA-256：
`82fb858cdbcf9146b1740a5cccd25dbf843ab9fbcdb88e05bbbbaed3e8e9cdd2`。
完整运行器和 LLDB 脚本都会核对该值，变化后应重新建立 ABI 依据。

本轮完整复现保存在 `local/apac-object-experiments/repro/`；`verification.json` 汇总验收，
`matrix.json` 保留数量与实际 Profile，`containers.json` 和 `asset_reads.json` 保留容器验证。
每个 case 的 `result.json`、stdout、stderr 保存命令、环境开关、耗时及逐阶段证据。

Core 接入应在 `AdmScene` 对象轨道被混合成输出 PCM 之前建立音轨／对象编号／时间线映射。
当前 `convert_to_apac` 只接收渲染后的声道或 HOA PCM，不应直接追加位置选项伪装成对象导出。
后续应单独决定私有接口使用政策、动态时基与 ADM 语义转换、多轨对象处理，以及能力拒绝行为。
LFE 的混合制作可行性已在后续报告中验证，产品级路由和播放校准仍需单独定义。
本轮不改变公开 C ABI、CLI、GUI 或生产编码流程；24 对象成功也不等于 17.1.6 布局或 LFE 映射完成。
