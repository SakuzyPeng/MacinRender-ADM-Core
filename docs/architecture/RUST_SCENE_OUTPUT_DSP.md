# Scene 输出 DSP（一期 1.4）

> 对应 [PCM 一致性审计](PCM_CONSISTENCY_AUDIT.md)一期 1.4，规则见 [ADR 0018](../adr/0018-scene-numeric-replay-rules.md) §3、§4。
> 证据在 [`evidence/pcm-consistency-1.4/`](evidence/pcm-consistency-1.4/)。

## 范围

1.4 处理 `SceneOutputSession` 交给设备的应用侧样本：HpTF、峰值保护和输出音量。
HpTF 与 `StereoPeakGuard` 的样本处理在 1.4 之前已经由 Rust 执行，本切片补齐剩余的 C++ 运算和平台数学函数，
并固定极小尾音清理的位置。HpTF → 峰值保护的顺序不变。

| 位置 | 改动 | 审计项 |
| --- | --- | --- |
| `SceneOutputSession::pull`：没有峰值保护、设备也没有自带音量时的音量乘法 | 移入 `mradm-dsp` `gain::scale`，每次回调跨一次 FFI；立体声路径的音量原本就在 Rust 峰值保护的 `pop` 中 | — |
| HpTF 极小尾音清理与非有限值恢复 | 从“每次处理调用末尾”改为“自 reset 起每 1024 帧”的固定网格；淡化在第 2048 帧精确结束 | S02 |
| HpTF 设计：双二阶系数、级联响应、极值搜索、自动衰减 | `pow`、`cos`、`sin`、`log10`、`asin` 改用 `libm`；`Complex64::norm` 内部的平台 `hypot` 改为 `libm::hypot`；`sqrt` 保留 std | N16 |
| `StereoPeakGuard` 释放系数 `1 - exp(-1 / (0.1·rate))` | f32 `exp` 改为 `libm::expf` | N17 |

1.4 之后，`SceneOutputSession` 中不再有决定样本值的 C++ 浮点运算，只剩缓冲清零和拷贝。
GUI 显示用的 `cascade_magnitude_db` 与设计共用同一响应函数，也随之改用 `libm`。

## 提交与验证

| 提交 | 内容 | Linux x64 config A 相对前一提交 |
| --- | --- | --- |
| `caf6859` | 无峰值保护输出的音量乘法移入 Rust | 普通 431 个文件、诊断 23946 个文件逐位相同 |
| `8ee8f82` | HpTF 尾音清理改为固定帧网格 | 同上，全部相同（回放信号达不到清理阈值） |
| `877a383` | HpTF 设计与峰值保护释放系数改用 `libm` | 同上，全部相同 |
| `5c0edf1` | HpTF 滤波循环改为按声道迭代 | 普通运行逐位相同；运算顺序不变 |

**音量。** 回放矩阵的设备路径都是立体声加峰值保护，走不到这条乘法。因此另加两层测试：
Rust 测试逐位比较 `gain::scale` 与直接乘积，覆盖 −0.0、次正规数和 `f32::MAX`；
C++ `mr_adm_stereo_peak_guard_tests` 构造无保护会话，确认音量 0.375 的输出逐位等于音量 1 的输出乘以 0.375，且输出超过 1.0 未被限幅。

**尾音清理网格。** 原规则在每次处理调用末尾检查：任一状态非有限，或全部状态绝对值不超过 `1e-20`，就清空历史。
因此调用方的分块决定了衰减尾音在哪里被清零，以及一个非有限样本污染输出多久。新规则：

- 每个级联自 reset 起计帧，只在 1024 的整数倍处检查；
- 非有限输入最多影响到下一个检查点（≤ 1023 帧），之后历史清空；
- 淡化在第 2048 帧精确结束，不再等到跨过它的块末。

`Processor` 的输出因此与调用分块无关，前提是目标在同一帧被接纳。
新测试用 6 种分块（含单帧、1023/1025/2047 交替）逐位比较，信号含一个 NaN、一段衰减到阈值以下的尾音和一次固定帧的淡化；
在旧实现上该测试失败。锁定矩阵的设备回放信号始终远高于阈值，也没有非有限值，因此输出不变。

Scene 设备回放的固定分块与碎片分块之间仍有差异，来源是输入侧的 Scene 渲染分块，不在 HpTF；输入分块与控制接纳时序属于 1.5。

**`libm`。** 在 Linux x64 上与 glibc 比较：

- 20000 个随机 HpTF 配置（1–10 段、7 种类型、44.1/48/96 kHz、两种前级策略）的双二阶系数、前级增益和自动衰减量全部相同；
  只有 111 个配置的 `max_response_db` 元数据相差 ≤ 5 ulp。
- 整数采样率 1–768000 中，`expf` 有 9209 个相差 1 ulp，均不是常用采样率。

所以 Linux 上的 PCM 不变；变化的意义在于各平台此后得到同一结果。

**三平台。** `877a383` 的 Consistency 运行 38570610669 与 CI 38570614580 通过：

- A/B 两种配置下 188 个 PCM id 三平台相同，门禁无失败；
- 全部 160 个内核文件三平台相同；
- 诊断运行中设备侧与 HpTF 的 44 个检查点三平台相同，仍有差异的只有三期的 `ear-hoa`、`ear-5_1-hoa-input` 检查点和 84 份 EAR f64 内核检查点。

HpTF 设计内核的 4 个观察文件（`hptf-{44100,48000}` 的输入与系数）因此设为门禁，内核门禁从 151 份增至 155 份。

## 性能

在共享 4 核 Linux 虚拟机上，用绑定单核的 Release 测试程序交替运行切片前（`528a0d5`，HpTF 与峰值保护源码与 `0ef1a01` 相同）
和 `5c0edf1` 共 8 轮，每轮取 21 次的中位数：

| 测量 | 切片前 | 切片后 | 比值 |
| --- | --- | --- | --- |
| 10 段配置的 HpTF 设计（含自动衰减） | 144.7 µs | 165.9 µs | 1.146 |
| `Processor::process`，20 s 48 kHz 立体声，511 帧一次调用 | 79.4 ms | 82.9 ms | 1.043 |

- 设计耗时增加来自纯 Rust 的 `libm`。设计只在控制线程发布新配置时执行，每次约 0.17 ms，不在音频回调中。
- 处理耗时在固定网格切分后一度上升约 10–20%，原因是拆出的滤波函数仍按帧计算交错下标；`5c0edf1` 改为按声道迭代后回到 1.043。
  这相当于单核约 0.4%，每 10 ms 块约 2 µs。
- 峰值保护的释放系数只在构造时计算一次；音量路径每次回调多一次 FFI 调用。两者都未单独计时。

原始数据与测试程序源码见 [`hptf-benchmark.json`](evidence/pcm-consistency-1.4/hptf-benchmark.json)，
差异扫描见 [`libm-sweep.json`](evidence/pcm-consistency-1.4/libm-sweep.json)。

## 剩余

- HpTF 目标在下一次处理调用接纳（S04），欠载与补零规则（S05），以及 Scene 输入分块，都属于 1.5。
- 文件流式渲染的实时监听共用同一套 Rust HpTF 与峰值保护，本切片的规则变更同样适用；
  其自有的音量与 dB 入口（`resolve_live_channel_gain`、HOA override）属于三期。
- 剩余 5 个内核观察文件为 EAR 布局输入 3 个、Scene 输入/输出 2 个。
