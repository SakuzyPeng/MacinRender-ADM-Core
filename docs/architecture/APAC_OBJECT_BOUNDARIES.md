# APAC 对象数量续测：编码与默认解码的不同边界

2026-09-25 本地产物已清理。本文的 `local/` 路径为历史运行位置；
精选结构化结果见[数值证据](evidence/apac_objects/README.md)。

验证日期：2026-09-22。环境仍为 macOS 27.0 / 26A428、AudioCodecs.component 7.0。

**此前的 7／32／128 是每个对象组件的能力数量项，不能直接当作整个文件的对象总数上限。**
通过多个组件，默认能力表下已完成 70 个对象的原生 AudioCodec 音频与位置读回；
71 个对象在系统默认元数据输出缓冲区处失败。纯编码能到达更高数量，不能与完整解码成功混为一谈。

## 1. 现在可以确认的结果

| 层次／配置 | 实测结果 | 结论范围 |
| --- | --- | --- |
| 单对象组件，默认能力表 | 7 成功，8 拒绝 | 首轮单组件结果 |
| 单对象组件，诊断 Level 1 | 32 成功，33 初始化 `!stt` | 每组件能力边界 |
| 单对象组件，诊断 Level 2 | 33、64、65 完整通过；127 编码完成 | 127 的默认解码没有完整通过 |
| 单个 `Object Count=128` | `acs ` 返回 `!dat` | 字典接受的数量为 0～127，不能把 0 解释为 128 |
| 两组件 `7+7`，默认能力表 | 14 对象完整通过，实际 `5/0` | 默认入口的总数可以超过 7 |
| 两组件 `32+32`，诊断 Level 1 | 64 对象完整通过，实际 `5/1` | 总数可以超过该级每组件的 32 |
| 每组件最多 7，默认能力表 | 64、70 完整通过，实际 `5/0` | 当前原生默认解码管线的成功样本 |
| 71 对象，默认能力表 | 编码完成，默认解码失败 | 首帧需要 4128 字节，缓冲区只有 4096 字节 |
| 128 对象，拆为 `18×7+2`，默认能力表 | 编码、排空和 cookie 获取完成，实际 `5/0` | 仅编码完成，未据此宣称默认回放可用 |
| 129 对象，拆为 `18×7+3`，默认自动布局 | 初始化 `!dat` | 另一层自动 Discrete 布局总数检查 |
| `64+64`、`65+64`，诊断 Level 2 | 128、129 编码完成，默认解码失败 | 128 不是整个文件的格式上限 |
| 214、215、252，两个组件，诊断 Level 2 | 已产出包，但 cookie 大小查询返回 `!buf` | 不算完整编码成功，诊断编码的真正上限尚未确定 |
| 253 音频＋3 元数据通道 | `acs ` 返回 `!dat` | 仅配置反例：该通道映射不能包含末尾索引 255 |

“默认能力表”下仍使用私有 `acs ` 对象配置，不代表 Apple 公开支持对象制作。
默认自动布局路径的 128／129 边界、每组件数量边界、解码元数据缓冲区边界是三件不同的事。
没有穷举其它布局表达、对象元数据组织或系统版本，因此不宣称已确定 APAC 格式的绝对上限。

## 2. 为什么多组件可以超过表中的数量

反汇编和对照实验均确认，`ProfileLevelConfig::GetLevelFromCodecConfigs` 遍历各个 `IASCConfig`，
分别将该组件的数量与等级表比较；不是先把所有对象组件的数量加起来再比较。
私有设置字典的 `ASComponents` 可包含多个 `Object` 项，各自指定数量及互不重叠的音频通道范围。

例如 70 对象使用十个 `Object Count=7`，音频范围依次为 `0..6`、`7..13`，直到 `63..69`。
对象元数据的组编号仍在文件内按音频通道顺序排列为 `0..69`。
70 对象的全部 560 条有效位置更新、音轨编号、独立测试音频率均通过检查；
最大方位误差约 0.334821°，最低预期频率能量占比约 **99.82787%**。

默认入口对自动 Discrete 输入布局还有总数检查。其结果与最终选择 `Profile 5 / Level 0`
不是同一个判定；本轮 128 对象分组编码成功、129 对象在初始化时被拒绝，不能用“每组件 7”解释。
这些检查只说明已测试的自动布局路径；不据此推断所有可构造配置的绝对编码上限。

## 3. 保持系统默认解码时的限制

按用户要求，解码器保持系统默认能力和配置。没有修改解码能力表、元数据缓冲区或系统组件文件。
早期对 `mdpf` setter 的试探被系统以 `nope` 拒绝，没有成功设置；该设置入口已从最终工具移除。
调试器仅观察解码数据、调用和容量检查。

`APACMetadataSink::Process` 在重建元数据后，将所需大小与其缓冲区比较。实测如下：

| 对象数 | 首帧所需字节 | 默认容量 | 原生解码结果 |
| --- | ---: | ---: | --- |
| 65 | 3780 | 4096 | 成功 |
| 70 | 4070 | 4096 | 成功 |
| 71 | 4128 | 4096 | 失败 |
| 85 | 4940 | 4096 | 失败 |
| 127 | 7376 | 4096 | 失败 |

这些样本的首帧大小符合 `58*N+10`，因此该表达方式在 70／71 之间跨过容量边界。
这是当前全部对象独立位置更新方式的实测边界，不是对所有元数据表达方式的通用定理。
失败先发生在元数据输出侧，内部返回 8，外层原生解码调用报告 `-50`。
没有通过扩大缓冲区、关闭元数据、跳过坏帧或改变解码能力表来把这些失败样本记成成功。

AVAssetReader 需要单独看待：

- 70 对象的 CAF 和 MP4 都返回 8192 帧、70 通道，但当前读取配置没有保留逐对象的独立测试音映射；
  最低对应频率能量占比约 7.89%。它不能直接代替本轮原生 AudioCodec 的逐对象 PCM 抽取。
- 71 对象仍可能报告读取完成、输出非静音，但只返回 **6144 帧**，少于应有的 8192 帧。
  127／128／129 的早期 CAF 读取也出现相同缺帧现象，不能仅用完成状态或 RMS 判定成功。
- 本轮“70 对象完整通过”明确指原生 AudioCodec 音频、从码流解码的对象位置及独立验证；
  不代表普通播放器直接空间回放或 AVAssetReader 原始对象抽取已通过。

## 4. 数据与工具变化

边界样本为 48 kHz、8192 个有效采样点（约 0.170667 秒），使用整数 FFT 频点上的独立单音。
选用完整 1024 点帧，避免多元数据通道在最后一帧被截断，并控制磁盘占用和调试开销。
所有对象位于水平面、距离 1，方位分布在约 ±150° 内。
原生解码包括 2048 帧前导，验证时依据实际 packet timing 截取有效的 8192 帧。

生成器增加了多组件配置、可选帧数及多个 PCM 元数据通道。
元数据按最后一个元数据通道优先的顺序，每通道每帧承载 1024 个 16 位字。
32 对象强制使用两个元数据通道的对照也完整通过，排除了“只要有两个元数据通道就失败”的解释。

共保存 24 组主边界组合、通道映射反例及额外的只读容量／容器观测。
`verification.json` 中的 `all_checks_passed` 表示成功与预期失败均已核对，**不是所有数量都能回放**。
失败在字典设置、初始化、cookie 获取和默认解码阶段分别记录，不合并成一个最大对象数字。

## 5. 复现及产物

沿用已有优化版探测程序，在新目录执行：

```sh
python3 scripts/research/apac_objects/run_boundaries.py \
  --output local/apac-object-experiments/new-boundaries \
  --reference local/apac-object-experiments/repro
python3 scripts/research/apac_objects/finish_boundaries.py \
  --output local/apac-object-experiments/new-boundaries \
  --reference local/apac-object-experiments/repro
```

已有结果位于 `local/apac-object-experiments/boundaries/`，可独立重新核验：

```sh
python3 scripts/research/apac_objects/verify_boundaries.py \
  --output local/apac-object-experiments/boundaries
```

`boundaries.json` 保存每组编码、原生解码及逐对象验证结果；`decoder_capacity.json` 保存 70／71 的实际容量观察；
`container_boundary_reads.json` 和 `asset_pcm_semantics.json` 分别保存帧数与 AVAssetReader 音频语义检查。
编码诊断仍仅对自建编码实例替换能力表；所有解码检查都保持系统默认。
新增内容仍为研究工具和报告，没有修改 Core 的生产导出、公开 C ABI 或 GUI。
