## 已排查：不必要的 GPU FFT

上轮换房的插桩记录共 1819 个主 GPU 批次，包含预热和两套房间：

| 房间实例 | 批次 | 无目标更新 | 无更新且无卷积任务 |
|---|---:|---:|---:|
| 原房间 | 859 | 616 | 373 |
| 新房间 | 960 | 555 | 151 |

其中 524 个批次没有目标更新或卷积任务，仍执行完整的响应／目标／输出 FFT 图。
无更新但仍有卷积的块也执行了不需要的响应和目标 FFT。

候选为这两类增加准备期建立的 Graph：无更新时保留历史和卷积，完全无任务时只更新／重置
输入历史，完成原同步后输出零，不做输出 FFT 或 D2H。没有改变 FIR、目标时序、尾声或延迟。
私有 DLL 单独修改；Rust 基准和回放程序沿用上轮冻结二进制。

[原生状态回归工具](../../scripts/research/room_gpu/empty_graph_test.py) 验证了 23 个块与旧 DLL
逐位一致：无任务时仍写入输入历史，后续目标能使用该历史，静音输出不会误清历史，reset
丢弃旧 epoch，之后可再次预热／卷积。零声源批次也通过。该回归不是完整 Session 声学验收。

## 新定位：淡化阶段的声源 EQ

五次超时的含预热调用序号恰好是 `147、151、155、159、163`，每四次调用一次。
同一输入序列中，换房请求在调用 64；原有预热为 41984 帧、82 次调用，因此淡化覆盖调用
146–164。五次超时均在这个窗口，且都落在 2048 帧长分区的刷新边界。
反射更新和晚场也有同周期工作，因此仅凭序号不能认定 EQ 是原因。

随后对**已提交基线**做一次独立 Windows Release 剖析，开启 `room-profile` 和 `ROOM_GPU_TRACE`，
另在每个声源的直达／湿声 `Long::process` 外添加 `source_eq` 墙钟计时。计时改动只存在于
临时诊断源码，未应用到本地运行时代码；[诊断补丁](evidence/room-gpu-switch/source-eq-diagnostic.patch)
和 [完整诊断结果](evidence/room-gpu-switch/source-eq.json) 单独保存。

| 调用序号 | phase | 调用墙钟 ms | EQ 调用数 | EQ 累计 ms | 声源处理累计 ms | EQ 占比 | 主 GPU 完成等待 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 147 | 2 | 5.9018 | 256 | 14.4572 | 17.9097 | 80.72% | 0.4496 |
| 151 | 2 | 6.0824 | 256 | 16.5206 | 20.4394 | 80.83% | 0.2180 |
| 155 | 2 | 5.9802 | 256 | 14.2756 | 17.6357 | 80.95% | 0.3704 |
| 159 | 2 | 5.9196 | 256 | 16.2088 | 19.5439 | 82.94% | 0.4880 |
| 163 | 2 | 6.1283 | 256 | 14.8853 | 18.5375 | 80.30% | 0.1964 |

这里的 EQ／声源处理是各 worker 的累计墙钟，包含并行及嵌套，**不能与单次调用墙钟相加，
也不是“总调用时间的 80%”**。不过同一组声源任务内部的比值表明，EQ 占主要部分。
该诊断本身平均 3.247549 ms、最大 6.3131 ms、19 次超时；全部属于插桩诊断，不替代正式验收。

声源 EQ FIR 为 32768 taps，2048 帧长分区每四次 512 帧调用刷新一次。淡化时，32 个声源、
两套房间、直达／湿声两支形成 128 条 EQ 链；每次调用含两个 canonical block，所以记录到
256 次 EQ 处理。离开淡化后旧房间停用直达支路，诊断的 phase 3 对应 192 次 EQ 处理。
源码时序、调用计数、周期和阶段耗时相互吻合，声源 EQ 应成为下一轮优化重点。

下一步优先评估把声源 EQ 大分区成批交给 GPU，沿用原“生成未来输出、下一块消费”的时序；
同时评估在滤波器及历史完全一致时，跨两套房间复用同一声源的直达 EQ。
两个房间的湿声输入随淡化不同，不能直接当作同一历史；需要继续验证完整尾声、reset、分包
和舍入门槛。尚未实现或验证这两种后续方案，也没有证明可任意改变现有 EQ 算术。

## 复现与状态

候选构建沿用 [GPU 工具说明](../../scripts/research/room_gpu/README.md#完整-session-研究入口)，
在独立 DLL 文件名下构建补丁版本，保留基线 DLL 和冻结的无插桩可执行文件。
原生回归在 Windows 使用同一 fixture 和 kernels：

```powershell
python scripts/research/room_gpu/empty_graph_test.py --baseline $BASELINE_DLL `
  --candidate $CANDIDATE_DLL --fixture $PRIVATE_FIXTURE --kernels $GPU_KERNELS --cuda-bin $CUDA_BIN
& $ROOM_BENCH_EXE $ROOM96 1024 512 32 --hrir $COLLECTION --quality realtime --scenario switch `
  --gpu-dll $CANDIDATE_DLL --gpu-fixture $PRIVATE_FIXTURE --gpu-kernels $GPU_KERNELS
```

诊断补丁基于 `e7ace2a`，只增加计时，需单独输出诊断二进制。Cargo 使用
`--features room-gpu-experiment,room-profile`，DLL 使用 `/DROOM_GPU_TRACE`，然后运行
`512 512 32 --scenario switch` 并在参数末尾追加 `--trace`。不得把该结果当作无插桩性能。

两次 Windows 临时目录均已清理：原生候选仅覆盖 41 个任务文件；诊断覆盖核对 345 项，
恢复 87 个原文件、移除 258 个任务文件。两次原 HEAD 和 Git 状态均一致，诊断后 canonical
示例恢复为无插桩构建。已认证并清理本地 644,253,669 bytes 临时 fixture 和提交检查快照，
原资源及既有构建缓存保留。本轮后续调查、回归工具和报告尚未加入新的提交。
