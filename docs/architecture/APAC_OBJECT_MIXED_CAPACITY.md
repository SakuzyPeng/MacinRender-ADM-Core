# APAC 混合模式：BED 声道、组件与对象数量边界

2026-09-25 本地产物已清理。本文的 `local/` 路径为历史运行位置；
精选结构化结果见[数值证据](evidence/apac_objects/README.md)。

验证日期：2026-09-23。macOS 27.0 / 26A428，AudioCodecs.component 7.0，arm64e。
组件切片 SHA-256：`82fb858cdbcf9146b1740a5cccd25dbf843ab9fbcdb88e05bbbbaed3e8e9cdd2`。

**混合模式没有一个可同时取满的“最大 BED＋最大对象”数字。**
必须区分单个 BED 的声道数、多个 BED 的累计声道数、BED 组件数，以及对象元数据容量。
本轮所有解码器都保持系统默认；诊断组只提高自建编码实例的 Profile 上限。

## 1. 直接可用的结论

这里 BED 数量若未注明“组件”，均指音频声道数；LFE 也占一个 BED 声道。

| 编码条件 | 单个 BED 声道上限 | 已完整验证的混合组合 | 边界含义 |
| --- | ---: | --- | --- |
| 默认能力表，实际 `5/0` | 12 | `24 BED＋69 对象`，BED 拆为 `12+12` | 对象分成每组件最多 7 个 |
| 默认能力表，实际 `5/0` | 12 | `61 BED＋67 对象`；`127 BED＋1 对象` | 当前默认自动布局路径总音频到 128 路 |
| 诊断编码上限 `5/1`，实际 `5/1` | 24 | `24 BED＋69 对象`，单个 BED | 对象拆为 `32+32+5`，默认解码通过 |
| 诊断编码上限 `5/2`，实际 `5/2` | 64 | `64 BED＋69 对象`；`128 BED＋69 对象` | 后者使用两个 64 声道 BED，总音频 197 路 |
| 诊断编码上限 `5/2`，实际 `5/2` | 64 | `253 BED＋1 对象` | 四个 BED 为 `64+64+64+61`，总音频 254 路 |

因此，在本轮元数据表达方式下，混合对象数的相邻成功／失败边界为 **69／70**。
默认编码路径的累计 BED 声道数在保留一个对象时达到 **127**；诊断编码路径实测达到 **253**。
这不是说 127 BED 与 69 对象、或者 253 BED 与 69 对象可以同时使用。

单 BED 的默认 12／13 和诊断 Level 2 的 64／65 均完成相邻数量对照：前者通过，后者在编码初始化返回 `!stt`。
单个 24 声道 BED 混入对象时，默认编码同样返回 `!stt`；提高编码到 Level 1 后通过。
纯固定声道内容可选择的 Profile 31，不能用来替代这里含对象内容所需的 Profile 5。

能力表对每组件的对象项仍为 Level 0／1／2 的 7／32／128；
字典的单个 `Object Count` 只接受 0～127，而且默认解码还有更早的元数据容量限制。
不能把表中的 128 解释成当前混合文件可完整解码 128 对象。详见[纯对象数量报告](APAC_OBJECT_BOUNDARIES.md)。

## 2. 默认解码的元数据容量

只读观察 `APACMetadataSink::Process`，默认输出缓冲区仍为 **4096 字节**。
每个 BED 组件占一个 renderer group，每个对象也占一个组；BED 内的声道数不等于组数。
本轮固定 BED 组不提交位置更新，对象各自提交独立位置，更新时间单位为 1024 个采样点。

| BED 声道／组件 | 对象数 | 首帧元数据所需字节 | 原生解码结果 |
| --- | ---: | ---: | --- |
| 1／1 | 69 | 4041 | 全部通过 |
| 12／1 | 69 | 4041 | 全部通过 |
| 1／1 | 70 | 4099 | `decoder_produce = -50` |
| 24／2 | 69 | 4071 | 全部通过 |
| 25／3 | 69 | 4101 | `decoder_produce = -50` |
| 61／6 | 67 | 4074 | 全部通过 |
| 60／5 | 68 | 4102 | `decoder_produce = -50` |
| 127／11 | 1 | 395 | 全部通过 |
| 64／1，诊断编码 | 69 | 4041 | 全部通过 |
| 128／2，诊断编码 | 69 | 4071 | 全部通过 |
| 253／4，诊断编码 | 1 | 187 | 全部通过 |

这解释了为什么 `61+67` 能通过而同为 128 路的 `60+68` 失败，
也解释了为什么提高编码 Profile 不能自动解决第 70 个混合对象的解码问题。
未通过扩大解码缓冲区、关闭元数据、修改能力表或跳过失败包来绕过这些反例。

这些字节数与结论限定于本轮元数据内容、字段和表达方式，不是对所有 APAC 元数据的通用数量定理。

## 3. 总音频与组件数量是另外两层约束

默认自动 Discrete 输入布局下，`127 BED＋1 对象` 完成编码、排空、cookie 获取和默认解码；
`128 BED＋1 对象` 则在编码初始化返回 `!dat`。这复现了先前纯对象的 128／129 总音频边界。

提高编码 Profile 后，254 路总音频能够被默认系统解码器完整读回。
当前字典映射和 PCM 元数据输入方法还要占用至少一个元数据通道：
`253 BED＋1 对象＋1 元数据 = 255 输入通道` 通过；
再增一个 BED 声道使元数据索引达到 255 时，`set_acs` 返回 `!dat`。
所以 253 是本轮保留一个对象、使用一个 PCM 元数据通道的已测制作路径边界，
**不是默认解码器、APAC 格式或其它元数据输入方式的绝对 BED 上限**。

将 BED 全部拆成单声道组件又出现不同边界：

| 单声道 BED 组件数＋1 对象 | 编码 | 默认原生解码 |
| --- | --- | --- |
| 62＋1 | 完整完成 | 63 路音频和对象位置逐项通过 |
| 63＋1 | 完整完成 | 初始化 `!dat` |
| 64、79、87、89、90＋1 | 完整完成 | 初始化 `!dat` |
| 91、95、126、127＋1 | 已输出包，cookie 获取 `!dat` | 不算完整文件，不进入解码验收 |

因此 127 个 BED 声道通过，并不表示 127 个单声道 BED 组件也通过。
本轮将组件数失败定位到 cookie 获取或解码初始化，未声称已查明全部内部原因，
也未将这组单声道递增样本的 62／63 边界推广为所有组织方式的格式上限。

## 4. 验证方法及布局含义

复用原生 `AudioCodec` 探测器，以 `-O2 -g` 构建。每个用例独立进程，普通运行限时 30 秒，LLDB 观察限时 60 秒。
全部短样本为 48 kHz、8192 个有效采样点；依据编码 timing 去除实际 2048 帧前导，逐路检查帧数、有限值、能量和独立频率。
BED 内 LFE 使用低频，普通音频使用互不相同的整数 FFT 频点；显式分配组件码率，延续[已验证的 LFE 方法](APAC_OBJECT_LFE_MIXED.md)。
对象组编号在所有 BED 组之后连续排列；位置检查读取解码后的元数据，不使用容器坐标代替。

主矩阵共 21 组：12 组通过完整语义验证，9 组是按阶段核对的预期失败。
通过组共核验 3888 条有效位置记录；最低预期单音能量占比 **99.98717%**，最大方位误差 **0.346468°**，符合位置量化精度。
另保存 15 组快速组件数探测、一个末端通道映射反例，以及 4 个成功样本的 CAF／MP4：
8 次容器提取的压缩包、magic cookie、timing 均与原始编码结果一致。

大量 BED 采用重复标签：多个 BED 可重复同一组扬声器标签；超过 24 声道的单个 BED 也重复已知的全频标签。
这些是测试音频容量与逐路对应关系的压力样本，**不代表 64、128 或 253 个不同物理扬声器位置已定义或支持**。
没有用这些结果确认 17.1.6、播放器直接对象渲染、LFE 播放校准或新的 GUI 布局。

## 5. Core 接入建议与复现

Core 应分开保存 BED 组件、每组件声道标签、对象组件、对象全局编号以及元数据通道映射。
LFE 继续使用明确的 BED LFE 标签；采用已验证的组件码率配置。
默认导出先检查每组件数量和总音频通道，再检查实际元数据表达的解码可用性。
不要仅写一个 `objects <= 69` 或 `bed_channels + objects <= 128` 条件就宣称全部组合受支持。
诊断编码结果用于能力研究，不应无提示地成为产品默认。

源码位于 `scripts/research/apac_objects/`，结果位于 `local/apac-object-experiments/mixed-capacity/`。
使用包含当前优化版 `bin/codec_probe` 的参考目录，在新目录复现：

```sh
python3 scripts/research/apac_objects/run_mixed_capacity.py \
  --output local/apac-object-experiments/new-mixed-capacity \
  --reference local/apac-object-experiments/lfe --matrix
python3 scripts/research/apac_objects/finish_mixed_capacity.py \
  --output local/apac-object-experiments/new-mixed-capacity \
  --reference local/apac-object-experiments/lfe
```

对已有结果仅重新验证时，省略第二条命令的 `--reference`，不会再次执行编解码器。
`capacity.json` 含逐路测量、Profile、阶段和容量；`verification.json` 区分通过与预期失败；
`component_counts.json`、`containers.json` 分别记录组件数量和容器检查。
仍无生产 API、GUI、默认构建或常规 CTest 改动。
